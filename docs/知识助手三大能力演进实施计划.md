# 知识助手三大能力演进实施计划

> 本计划把三份差距分析收敛成一份**可执行、分阶段**的落地方案：
>
> 1. [ReAct 推理链路](../server/src/agent/index.js) —— 路线 A（P0 + P1）
> 2. [结构化知识库](../server/src/db/index.js) —— LLM Wiki（P0 最小闭环）
> 3. [Agent 记忆体系](../server/src/agent/sessionStore.js) —— 长期记忆 + 质量过滤（P0 + P1）
>
> 前置约定：**外部存储**（Supabase + Upstash Vector/Redis + BullMQ）稍后由你在 `server/.env` 配置，本次代码必须**先走适配器模式**，保证「本地可跑、切外部零改业务代码」。

***

| 工作流        | 本次交付                                                                                                                  | 后续（不在本次）             |

| 记忆体系       | P0：QA 长期记忆 + `searchHistoricalQA` + 异步写回；P1：质量过滤                                      P2 短期压缩 + `searchSessionMemory` | <br />               |

## 二、总体架构（三层并存 + 记忆旁路）

```
┌────────────────────────────────────────────────────────────┐
│ Agent（ReAct 循环 + 工具白名单）                              │
│   已有：search_documents / read_document          (RAG)     │
│   新增：lookup_entity        (LLM Wiki)                     │
│   新增：searchHistoricalQA / searchSessionMemory  (长期记忆/ │
│   短期记忆)                                                 │
└───────────────┬────────────────────────────────────────────┘
                │ 路由优先级：记忆 → 实体 → RAG
   ┌────────────┴──────────────┬──────────────────┐
   ▼ 短期/长期记忆             ▼ 结构化层           ▼ 文档层
  SessionStore                entities/relations   Document + RAG 索引
  + QA Memory Store(新增)     (新增, LLM Wiki)     (已有, 复用)
        │
   ┌────┴────────────────────────────┐
   │ 写回闭环（LLM 抽取 → pending → 复核）│
   │ QA 写回队列 / 知识抽取队列（复用 indexQueue 模式）│
   └─────────────────────────────────┘
```

三条线共享的基础设施（**先做地基，再并行三条**）：

- 向量库按 **namespace 隔离**：`doc`（已有）｜`entity`（新增）｜`qa`（新增）
- 异步队列泛化：`indexQueue` 的「串行 + 指数退避 + 审计 + 失败标记」抽成通用工厂
- Embedding 客户端工厂抽离，文档/实体/QA 三方复用同一 `embeddingModel` 与 API Key

## 三、外部存储策略（关键决策）

现状事实（已核实）：

- `../server/src/db/index.js` 为内存实现，仅对 `hosted/supabase` 做**异步 best-effort 元数据同步**（目前只有 `insertDocument/deleteDocumentById`）。
- `../server/src/services/vectorStore/index.js` 支持 `local`（JSON 文件）与 `upstash` 两套适配器，但**尚未引入 namespace 隔离**。
- `../server/src/services/indexQueue.js` 已支持 `memory` 与 `bullmq`（Upstash Redis）两种驱动。

**落地原则**：

1. **数据层**：新增的 `entities / relations / qaMemory` 三张「表」沿用 db 适配器模式（内存数组 + 自增 id），并补齐 `hosted.js / supabase.js` 的对应 upsert/delete 方法（先 stub，配置好外部库后再接真实 SQL）。
2. **向量层**：`vectorStore` 增加 namespace 参数，`upstash.js` 用 `Index.namespace(...)` 实现三库隔离；`local` 用三个独立 JSON 文件（`vectors.doc.json / vectors.entity.json / vectors.qa.json`）。
3. **队列层**：`indexQueue` 泛化为「按 job 类型区分」的通用队列，文档索引 / 知识抽取 / QA 写回三类 job 复用同一套退避与审计，BullMQ 下用不同队列名或 job.data.type 区分。
4. **切换成本**：env 配好后，唯一动作是设置 `DB_DRIVER / VECTOR_STORE / INDEX_QUEUE_DRIVER`，**不改业务代码**。

## 五、阶段 0 —— 地基（前置）

### 5.1 config/env 扩展

在 `../server/src/config/index.js` 与 `../server/.env.example` 新增：

| 环境变量                        | 默认      | 说明           |
| --------------------------- | ------- | ------------ |
| `AGENT_ENABLE_THINKING`     | `false` | ReAct 推理流开关  |
| `AGENT_MAX_REASONING_CHARS` | `4000`  | 推理段字符上限      |
| `WIKI_ENABLED`              | `false` | LLM Wiki 总开关 |
| `WIKI_EXTRACT_ENABLED`      | `false` | 文档发布后自动抽取    |
| `MEMORY_ENABLED`            | `false` | 长期记忆总开关      |
| `QA_MEMORY_TOP_K`           | `3`     | 历史 QA 召回条数   |
| `QA_MEMORY_MIN_SIM`         | `0.90`  | QA 去重相似度阈值   |

复用已有变量：`LLM_*`（抽取/QA 复用）、`EMBEDDING_*`（实体/QA 向量）、`VECTOR_STORE`、`UPSTASH_*`、`DB_DRIVER`、`INDEX_QUEUE_DRIVER`。

### 5.2 向量库 namespace 隔离

- `../server/src/services/vectorStore/index.js`：所有方法加 `namespace` 参数透传。
- `../server/src/services/vectorStore/upstash.js`：`Index({ url, token })` 基础上调用 `.namespace(name)`；无 namespace 时回退主空间。
- `../server/src/services/embeddingService.js`：本地 JSON 文件名与 `VECTORS_FILE` 解耦，按 namespace 生成 `vectors.${namespace}.json`；抽出一个 `getEmbeddings()` 导出工厂供实体/QA 复用。

### 5.3 队列泛化

- `../server/src/services/indexQueue.js` 抽 `createQueue({ jobType, handler })` 通用工厂；`indexQueue` 变为 `createQueue({ jobType: 'index', handler: upsertDocument... })`。
- 新增 `extractionQueue`、`qaWriteQueue` 复用该工厂（见阶段 2/3）。

**阶段 0 验收**：`VECTOR_STORE=local` 与 `upstash` 下，`doc/entity/qa` 三 namespace 读写互不串扰；三类队列 job 均可退避重试并落审计。

### 兼容性注意

`enable_thinking` 是**通义千问（DashScope）专属参数**。当前 `.env.example` 里 `LLM_BASE_URL` 指向 DeepSeek，`enable_thinking` 对 DeepSeek 不生效。因此：

- `AGENT_ENABLE_THINKING=true` 仅在 Qwen 模型上产生推理流，DeepSeek 下自动无推理、不影响正文。
- 若后续要在 DeepSeek 上做推理可见，需切 `deepseek-reasoner`（这属于路线 B 范畴，不在本次）。

### 验收标准

1. `AGENT_ENABLE_THINKING=true` + Qwen 模型时，前端可展开看到「思考中」过程。
2. 最终回答仍满足 `[Sx]` 来源校验（`registry.validate(text)` 只校验正文，不被推理干扰）。
3. 每次问答的 `reasoningChars` 进入审计日志；推理超限被截断，不影响正文。

## 七、阶段 2 —— LLM Wiki（P0 最小闭环）

### 7.1 数据层（Entity + Relation）

新增 `../server/src/db/knowledgeGraph.js`（与 `db/index.js` 并列，复用 `toNumberId` 等工具）：

```js
// 实体
entities = [{ id, name, type, aliases: [], summary,
  sources: [docId], status, updatedAt }]      // status: pending/confirmed/rejected
// 关系（有向，谓词可复用）
relations = [{ id, subjectId, predicate, objectId, sources: [docId], status, updatedAt }]
```

- 内存数组 + 自增 id；导出 `upsertEntity / listEntities / getEntity / confirmEntity / rejectEntity / upsertRelation`。
- 补齐 `../server/src/db/hosted.js`、`../server/src/db/supabase.js` 的 `upsertEntity / deleteEntityById`（先 stub）。
- **溯源 + 状态是硬约束**：LLM 写回一律 `status='pending'`，仅 `confirmed` 参与检索。

### 7.2 知识抽取任务

新增 `../server/src/services/extractionService.js` + `extractionQueue`：

```
文档发布（routes/documents.js，与 enqueueIndexJob 同处） → extractionQueue.enqueue(docId)
   │
   ▼
抽取 handler：读文档 → 调 LLM（复用 createModel 或低成本模型）抽取实体/关系 JSON
   │
   ▼
去重（按 name+type / aliases 归一）→ upsert（status=pending, sources=[docId]）
   │
   ▼
实体 summary 向量化 → 写入 entity namespace
```

- 抽取 prompt 内置于 `extractionService.js`，要求模型只输出结构化 JSON（name/type/aliases/summary/关系三元组）。
- 复用 `indexQueue` 的退避重试 + `audit("extract_job.*")`。

### 7.3 `lookup_entity` 工具

`../server/src/agent/tools.js` 的 `createKnowledgeTools` 内新增：

```js
lookup_entity: 按名称/别名查实体，返回 summary + 支撑文档（sources 解析为文档片段并 register）
```

- 只返回 `status === 'confirmed'` 的实体。
- 支撑文档片段走 `registry.register`，让回答能 `[Sx]` 溯源。

### 7.4 词条页 + 人工复核（最简）

- 新增 `../server/src/routes/entities.js`：`GET /api/entities`（列表/pending 列表）、`GET /api/entities/:id`、`POST /api/entities/:id/confirm|reject`（admin/editor 鉴权）。
- `../server/src/app.js` 挂载 `/api/entities`。
- 前端新增 `src/pages/entity/`：实体详情（summary + 来源文档链接）+ pending 复核列表（确认/驳回按钮）。

### 7.5 提示词

`../server/src/agent/prompts.js` 追加：可调用 `lookup_entity` 查结构化实体；所有写回为 `pending` 且带溯源（供后续抽取透明化说明）。

### 验收标准

上传一篇新文档后：系统自动抽出一批 `pending` 实体；人工确认后，Agent 能通过 `lookup_entity` 引用这些实体回答问题；每条实体可追溯到源文档。

## 八、阶段 3 —— Agent 记忆体系（长期记忆 + 质量过滤，P0 + P1）

### 8.1 QA 存储层

新增 `../server/src/db/qaMemory.js`：

```js
qaMemory = [{ id, question, answer, sources: [sourceId...],
  userId, sessionId, status, score, embedding, createdAt, updatedAt }]
// status: pending / confirmed / rejected
```

补齐 `hosted.js / supabase.js` 的 `upsertQa / deleteQaById`（先 stub）。

### 8.2 QA 向量库（与文档隔离）

新增 `../server/src/services/qaMemoryService.js`：

- 复用阶段 0 的 embeddings 工厂，把 `question + answer` 向量化，写入 `qa` namespace。
- `searchHistoricalQA({ userId, query, limit })`：在本人 `confirmed` QA 内做语义检索，返回带溯源的历史问答对。

### 8.3 `searchHistoricalQA` 工具

`../server/src/agent/tools.js` 新增工具，内部**强制按当前** **`userId`** **过滤**，且只召回 `confirmed`。

### 8.4 QA 异步写回（不阻塞 SSE）

- `../server/src/routes/agent.js` 阶段 4a 成功后、`finally` 之前，把「QA 向量化」入 `qaWriteQueue`，**绝不在 SSE 请求内同步 await**。
- handler：质量过滤（见 8.5）→ 向量化 → 写入 `qa` namespace + `qaMemory` 表。

### 8.5 质量过滤（P1，关键约束）

| 层级   | 触发                                                          | 结果                    |
| ---- | ----------------------------------------------------------- | --------------------- |
| 自动验证 | 回答 `completed` + 来源校验通过 + 非空 + 未触发 TOOL\_LIMIT/MODEL\_ERROR | `pending`             |
| 用户确认 | 点赞 / 采纳 /「有帮助」反馈                                            | `pending → confirmed` |
| 相似去重 | 新 QA 与已有 QA 向量相似度 ≥ `QA_MEMORY_MIN_SIM`                     | 不入库                   |

- 失败 / 取消 / 无来源 / 空回答一律不存。
- 检索默认只召回 `confirmed`。
- 用户确认信号需要前端反馈入口 + 后端接口（`POST /api/agent/messages/:id/feedback` 或复用现有点赞体系，按最小改动接入）。

### 8.6 来源编号兼容

历史 QA 的 `answer` 可能含 `[Sx]`。被召回回放时，需剥离或重新映射编号（复用 `sourceIsValid` 判断来源是否仍有效），避免与当前 `SourceRegistry` 冲突。

### 验收标准

1. 回答一次后，新会话问相似问题，Agent 能通过 `searchHistoricalQA` 命中历史解答并引用。
2. 只有被确认/验证的高质量 QA 进入可召回集；低质量/失败回答不污染检索。
3. QA 记忆按 `userId` 隔离，跨用户不可见。

## 十、风险与回滚

| 风险                       | 影响       | 缓解                                 |
| ------------------------ | -------- | ---------------------------------- |
| `enable_thinking` 换模型不通用 | 推理流不生效   | 开关可配，未开启回退无推理模式                    |
| LLM 抽取幻觉污染实体库            | 检索命中错误事实 | pending 审批 + 溯源 + 仅 confirmed 参与检索 |
| QA 低质量污染记忆               | 回答质量下降   | 质量过滤 + 只召回 confirmed + 相似去重        |
| 写回→检索→写回 自激              | 知识抖动     | 去重 + 幂等 upsert + 抽取/写回限流           |
| 切外部存储断档                  | 数据不一致    | 全部新数据层走适配器，阶段 0 先行验证               |
| 推理 token 成本暴涨            | 成本       | 独立计量 + `maxReasoningChars` 限长      |

**回滚原则**：三条线均以开关（`AGENT_ENABLE_THINKING / WIKI_ENABLED / MEMORY_ENABLED`）门控，任一功能异常可单独关闭，不影响现有 RAG 问答主链路。

***

> 结论：按「阶段 0 地基 → 三条线并行/串行」推进。地基先保证外部存储可无缝切换，再依次落地 **ReAct 推理可见（路线 A P0+P1）**、**LLM Wiki（P0 最小闭环）**、**记忆体系（长期记忆 + 质量过滤）**。所有写回都以 `pending + 溯源` 兜底，所有新能力以 env 开关门控，可灰度、可回滚。
