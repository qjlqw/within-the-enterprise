# 结构化知识库（Agentic KB）演进差距与方案

> 目标形态：一个「由 LLM 维护、面向 Agent 与人类共同消费的结构化知识库/维基」。
> 本文先盘点现状，再逐项对照目标找出差距，最后给出分阶段演进方案与关键设计决策。

## 一、目标形态定义

本文所讨论的「结构化知识库」由四个支柱构成：

| 支柱 | 含义 |
|---|---|
| 结构化 | 有 schema 的实体（Entity）+ 关系（Relation），而非整篇平铺文档 |
| LLM 维护 | Agent 能把知识**写回**：抽取、互链、去重、查矛盾、更新 |
| Agent 消费 | 检索优先，语义/图谱召回，可被工具调用、可多跳推理 |
| 人类消费 | 可读页面 + 词条互链 + 版本 diff |

缺其中任意一条腿，都只是「普通文档库」，不是「面向 Agent 的结构化知识库」。

## 二、现状盘点

### 2.1 数据模型（扁平文档）

文档核心字段见 `../server/src/db/index.js`：

- `id / title / content / category / tags / status / version`
- `authorId / views / likes / favorites`
- 版本快照 `documentVersions` + 回滚 `rollbackDocument`

文档是「一篇 Markdown」为单位，**没有实体/关系层级**。category 是单一分类、tags 是自由标签，都不构成结构化知识网络。

### 2.2 存储

`../server/src/db/index.js` 采用「内存实现 + 可选托管」，通过 `DB_DRIVER`（`local / hosted / supabase`）切换。这意味着新增数据层必须遵循同样的适配器模式，否则切到 Supabase 时会断档。

### 2.3 检索（Agent 消费侧，已完成）

RAG 链路完整：

- 解析：`../server/src/services/documentParser.js`（.md/.txt/.docx）
- 切片 + 向量化：`../server/src/services/embeddingService.js`
- 向量库：`../server/src/services/vectorStore/`（local / Upstash）
- 混合检索 + 精排：`../server/src/services/knowledgeService.js`（`searchDocumentsHybrid`）
- 异步索引：`../server/src/services/indexQueue.js`

### 2.4 Agent（只读）

`../server/src/agent/tools.js` 只暴露两个只读工具：

- `search_documents`：混合检索
- `read_document`：按 id 读正文

系统提示词 `../server/src/agent/prompts.js` 明确约束「只能使用已注册工具，不得创建、修改或删除文档」。来源校验通过 `SourceRegistry` + `[Sx]` 引用完成（`../server/src/agent/events.js`）。

## 三、差距分析

对照四支柱，现状完成度：

| 支柱 | 现状 | 缺口 |
|---|---|---|
| 结构化 | ❌ 扁平文档，无实体/关系 | 需要 Entity + Relation 数据层 |
| LLM 维护 | ❌ Agent 只读，无写工具、无回写闭环 | 需要写回流程 + 写工具 |
| Agent 消费 | ✅ 混合检索 + rerank | 缺图谱多跳召回 |
| 人类消费 | ⚠️ 文档管理/版本/UI 有，无互链 | 缺词条互链 + Wiki 展示 |

**两个决定性缺口：**

1. **写回闭环缺失**：Agent 答完题不沉淀知识，每次冷启动；文档全靠人手工上传/打标/分类；无「抽取 → 写回 → 下次检索命中」的飞轮。
2. **结构化缺失**：检索基于文本相似度 + 关键词，是「文本匹配」，无法表达「部门 A ↔ 制度 B」这类关系，无法跨文档多跳聚合（GraphRAG），无法做去重/矛盾检测。

## 四、目标架构

在现有「文档层」之上，新增「结构化层」，三层并存：

```
┌─────────────────────────────────────────────┐
│  人类消费层：词条页 / 互链 / diff            │  ← 新增 Wiki 展示
├─────────────────────────────────────────────┤
│  结构化层：Entity（实体）+ Relation（关系）   │  ← 新增，本次核心
├─────────────────────────────────────────────┤
│  文档层：Document + 版本 + RAG 索引          │  ← 已有，复用
└─────────────────────────────────────────────┘
         ▲
  写回流程（LLM 抽取 → 入库 → 重建索引）
```

### 4.1 结构化数据模型（最小可用）

```js
// 实体
entities = [{
  id, name, type,            // 如 { name: '技术部', type: 'department' }
  aliases: [],               // 别名，用于归一化
  summary,                   // 实体一句话摘要（供检索 + 词条页）
  sources: [docId],          // 溯源：该实体由哪些文档支撑
  status,                    // pending / confirmed / rejected（人工复核）
  updatedAt
}]

// 关系（有向，谓词可复用）
relations = [{
  id, subjectId, predicate, objectId,  // 如 (技术部) --负责--> (前端平台)
  sources: [docId],                    // 溯源
  status, updatedAt
}]
```

「溯源 + 状态」字段是关键：LLM 写回的内容必须先落在 `pending` 状态，由人类确认后转 `confirmed`，否则幻觉会污染知识库。

### 4.2 写回闭环

```
问答结束
   │
   ▼
(异步) 抽取任务：LLM 从本轮问答 / 新发布文档中抽取实体与关系
   │
   ▼
去重 + 冲突检测（复用 sourceIsValid 思路）
   │
   ▼
upsert 到 entities / relations（status = pending）
   │
   ▼
实体 summary 重新向量化入库（供后续检索命中）
   │
   ▼
人类在词条页确认 / 驳回 → status 变更
```

### 4.3 检索升级（GraphRAG 多跳）

在 `searchDocumentsHybrid` 之前或之后增加图谱召回：

- 命中实体 → 沿关系边取 1~2 跳邻域实体 → 读取其支撑文档片段
- 回答「部门 A 与制度 B 的关联」时，先定位实体、再沿边遍历，最后落到文档

## 五、分阶段演进方案

### P0 —— 跑通「LLM 维护」最小闭环（验证价值）

- [ ] 新增 `entities` / `relations` 两张「表」及 CRUD（沿用 db 适配器模式）
- [ ] 新增异步「知识抽取」任务：问答结束或文档发布后，调 LLM 抽取实体/关系
- [ ] 实体/关系入库为 `pending` 状态，附 `sources` 溯源
- [ ] 新增只读工具 `lookup_entity`，让 Agent 能查结构化实体
- [ ] 词条页最简版：展示实体 + 其来源文档

**验收**：上传一篇新文档后，系统能自动抽出一批实体，Agent 能引用这些实体回答问题，且所有写回都有溯源、可复核。

### P1 —— 结构化检索（多跳）

- [ ] 实体 `summary` 向量化，纳入混合检索召回
- [ ] 关系边存储 + 1~2 跳图遍历，实现多跳召回
- [ ] 去重 / 别名归一化 / 矛盾检测（两篇文档对同一实体结论冲突时标记）
- [ ] `search_graph` 工具，供 Agent 沿关系查询

**验收**：能回答跨文档的关联型问题（「负责 X 的团队有哪些相关制度」），并给出多跳路径作为证据。

### P2 —— Wiki 化（人类消费）

- [ ] 词条互链（`[[实体名]]` 语法解析为内链）
- [ ] 实体页 diff / 变更历史（复用现有版本快照思路）
- [ ] 写回内容的人工复核工作流（批量确认/驳回）
- [ ] 矛盾与「无来源」实体告警

**验收**：人类可像 Wiki 一样浏览/编辑词条，且 LLM 的每次写回都透明可追溯。

## 六、关键设计决策

### 6.1 写回时机：同步工具 vs 异步任务

**推荐异步**。理由：

- 写回不应阻塞问答响应（抽取是额外一次 LLM 调用，有成本与延迟）
- 便于统一做去重、冲突检测、失败重试（复用 `indexQueue` 的退避重试模式）
- 可对写回做独立限流与审计

### 6.2 图谱存储：关系表 vs 图数据库

**推荐先用关系表（edges 表）**，沿用现有 `local / hosted / supabase` 适配器，不引入 Neo4j 等新依赖。数据量到「千万级关系、需要深度图算法」再考虑专用图库。

### 6.3 写回可信度：pending 审批 + 溯源

LLM 写回一律 `pending`，必须满足：

- 每条实体/关系带 `sources: [docId]` 溯源
- 只有 `confirmed` 状态才参与 Agent 检索（避免幻觉污染）
- 复用 `sourceIsValid` 校验思路：来源文档改版/删除后，派生实体自动降级为「待复核」

### 6.4 权限与安全

- 写工具/写回流程不得突破现有权限模型（作者/admin）
- 所有 LLM 写回走 `audit` 审计（复用 `../server/src/services/observability.js`）
- 系统提示词中「只读」约束需改为「可写回，但只能写入 pending，且必须附溯源」

## 七、风险与权衡

| 风险 | 影响 | 缓解 |
|---|---|---|
| LLM 幻觉污染知识库 | 检索命中错误事实 | pending 审批 + 溯源 + sourceIsValid 降级 |
| 写回→检索→写回 循环放大 | 知识自激、版本抖动 | 去重 + 幂等 upsert + 抽取限流 |
| 抽取成本/延迟 | 每次写回多一次 LLM 调用 | 异步 + 批量 + 只对新发布文档抽取 |
| 图谱与文档不一致 | 实体指向过期文档 | 复用索引队列，文档变更联动重建 |
| 过度设计 | 结构复杂、维护成本高 | P0 只做最小闭环，验证后再扩展 |
