# 重排项目排期 Review

## 结论

[进阶langGraph和人机协同计划方案.md](进阶langGraph和人机协同计划方案.md)方案整体“技术上可实现”，但对当前项目来说明显偏大，且优先级需要重排。

当前项目适合先把 **RAG 质量、文档输入、可观测性和数据持久化** 做好，再考虑 LangGraph、MCP、多 Agent 等高级能力。

这份方案更适合作为“能力储备清单”，不适合作为当前项目的直接开发排期。最值得保留的是 **Rerank、基础文档解析和评估体系**；最应推迟的是 **MCP 反向服务、多 Agent、长期记忆以及没有实际审批场景支撑的 HITL**。

---

## 当前实际基础

- 已有 LangChain `createAgent` + ReAct + middleware，支持流式 SSE、工具调用限制、重试、引用校验。  
  见 `server/src/agent/index.js:30`。

- 已有本地 JSON 向量库和混合检索，但 `RAG_TOP_K` 配置目前没有真正被使用，实际是按请求 `limit * 2` 召回。  
  见 `server/src/services/knowledgeService.js:90`。

- 会话仍是进程内存结构（重启后会话丢失），但数据库已切换为 Supabase 持久化，用户、文档等业务数据不再因重启丢失。  
  见 `server/src/agent/sessionStore.js:17`（会话）与 `server/src/db/supabase.js`（数据库）。

- 文档接口目前只有 JSON 内容创建，没有 PDF / Word 上传；`multer` 只用于头像。  
  见 `server/src/routes/documents.js:117`。

- 当前没有安装 `@langchain/langgraph`、MCP SDK 或 MCP LangChain 适配器。

- 现有测试实际通过了 17 个用例（本次改造前基线），说明当前 ReAct、引用、会话和取消流程已经比较完整；改造后全套测试为 43 个用例全部通过（见下文「已完成工作总结」）。

## 逐项判断

### Rerank

- **判断**：可行，价值较高。
- **建议**：建议做，但先确认 DashScope 的真实 rerank endpoint 和返回格式。
- **注意**：
  - 召回候选应独立配置，不能只改 `RAG_TOP_K`。
  - 需要保留现有融合排序作为降级。
  - 用 Recall@K、MRR、引用正确率验证收益。

### 文档解析

- **判断**：可行，而且比多 Agent 更实用。
- **建议**：先支持 Markdown、TXT、DOCX，小文件 PDF 后置。
- **注意**：
  - `pdf-parse` 主要是 Buffer 解析，方案中“100MB+ 流式分页读取”不能直接靠它实现。
  - 还要补 MIME 检测、大小限制、异步索引、失败重试和索引状态。

### LangGraph + HITL

- **判断**：有条件可行。
- **建议**：只有在出现“审批、写入、权限变更”等真实人工确认场景时才值得迁移。
- **注意**：
  - 当前工具全部只读，没有 `needsApproval` 行为，HITL 暂时没有业务价值。
  - `MemorySaver` 也不能解决重启和多实例恢复。

### MCP

- **判断**：当前不建议做。
- **建议**：当前没有外部工具需求，暂缓。
- **注意**：
  - `loadMcpTools` 通常需要 LangChain 的 MCP adapter，不是只安装 `@modelcontextprotocol/sdk` 就够。
  - 反向暴露 MCP Server 会扩大权限和安全边界，应最后考虑。

### Plan-and-Execute

- **判断**：暂缓。
- **建议**：当前问答规模较小，ReAct 已能完成搜索和正文读取。
- **注意**：方案中让“Reranker 判断是否重新规划”概念不准确，Reranker 是文档排序器，不是计划评估器。

### Supervisor Multi-Agent

- **判断**：暂缓，基本属于过度设计。
- **建议**：当前只有两个只读工具，没有检索、总结、视觉等真正独立的 Agent 边界。
- **注意**：
  - CV Agent 也不对应现有产品能力。
  - 会显著增加 Token、延迟、调试和死循环风险。

### 语义缓存

- **判断**：可行，但不应列为 P0。
- **建议**：需要把历史上下文、模型版本、Prompt 版本、检索索引版本、权限范围纳入缓存键。
- **注意**：
  - JSON 文件还存在并发写入、损坏、无限增长和 O(n) 遍历问题。
  - 建议先做精确缓存或短 TTL，再评估语义缓存。

### 长期记忆

- **判断**：当前不建议做。
- **建议**：企业知识助手首先应该保证“基于权威文档回答”，跨会话记忆可能引入隐私和错误偏好。
- **注意**：当前用户数据本身也是内存存储，单独把 memory 写文件会产生持久化不一致。

## 方案中需要直接修正的地方

1. `RAG_TOP_K=20` 目前不会生效；`server/src/config/index.js:59` 中的 `topK` 没有传入 `semanticSearch`。

2. 当前工具 `limit` 最大为 10，默认是 5；默认混合检索实际最多召回 10 个向量片段，不是固定 top-20。

3. `SourceRegistry` 包含 Map 和回调，不应直接放入 LangGraph checkpoint state；应只保存普通 JSON 来源记录，恢复时重建 registry。

4. `MemorySaver` 只是内存检查点，不能支持真正的断线恢复、服务重启恢复或多实例部署。

5. 文档解析方案没有处理当前内存数据库的持久化问题；文件上传后服务重启仍会丢文档。

6. `server/.env.example` 中存在疑似真实格式的 API 凭据，建议立即移除并轮换相关密钥。

## 最终建议

建议按以下优先级推进：

1. **P0**：基线与可靠性。
2. **P1**：RAG 质量与数据入口。
3. **P2**：按真实业务需求引入 LangGraph。
4. **P3**：按需求选择高级能力。

最值得保留的是 **Rerank、基础文档解析和评估体系**；  
最应推迟的是 **MCP 反向服务、多 Agent、长期记忆**，以及没有实际审批场景支撑的 **HITL**。
