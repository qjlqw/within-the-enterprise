# 摘要

本次评估覆盖该项目的服务端 39 个源文件、前端 43 个源文件、6 个数据库迁移脚本以及前后端两份依赖清单，并对版本库跟踪状态、运行配置和依赖漏洞做了命令行实测。结论是：项目存在漏洞，问题并非零散的编码瑕疵，而集中在身份与密钥治理、输入输出信任边界、单实例假设三处结构性缺口。按统一口径共确认 40 项可在代码中定位的风险点，其中严重 3 项、高危 10 项、中危 18 项、低危 9 项；依赖层面另有服务端 4 项、前端 2 项已知漏洞。

三项严重问题都具备直接可利用性。其一，仓库中提交的 server/.env.example 的 JWT\_SECRET 与运行环境 server/.env 的实际值完全一致，实测为 36 位同值，任何能读取仓库的人都可以签发任意用户的令牌，包括管理员。其二，文档详情页使用 MDEditor.Markdown 渲染正文，该组件的依赖链包含 rehype-raw，会把文档中的原始 HTML 直接渲染；配合开放注册与令牌存储在 localStorage，一篇恶意文档即可在他人浏览器执行脚本并窃取管理员令牌。其三，PUT /api/documents/:id 把请求体原样交给 updateDocument，而后者对 title、content、category 没有兜底，只提交部分字段就会把未提交的字段写成空值，同时推进版本号并写入残缺的版本快照。

十项高危主要分布在访问控制与成本放大两个方向。访问控制上，环境变量文件未被 .gitignore 忽略、登录与注册接口没有任何频率限制且使用同步 bcrypt、Supabase 未启用行级安全、头像上传只校验客户端声明的 MIME 类型。成本上，关键词检索不分页地把全部已发布文档连同正文拉进内存，单轮最多执行 3 次；工具调用上限默认 300，而示例配置写的是 30；每轮问答固定叠加两次向量化与一次精排。按配置上限推算，单轮问答最坏可触发 8 次模型调用、约 25 万输入 token，是典型轮次的五倍以上。此外，浏览量、点赞、收藏与积分全部是读改写非原子操作，分页参数普遍没有上限。

建议按关边界、加限流、收信任、控成本的顺序推进：一周内闭环三项严重与四项访问控制高危，两到四周完成成本护栏与数据一致性改造，一到两月补齐检索下推、配额计量与回归测试。需要说明的是，本次为静态审查，未对运行中的服务发起爆破、注入或越权验证；成本结论依据配置上限与代码调用路径推算，不含真实账单数据；依赖结论仅覆盖当前已安装的依赖树。上述限制意味着部分中低风险项的实际影响可能高于或低于本文判断，需在联调环境复测。

# 1　评估范围与方法

## 1.1　评估范围

评估对象为仓库主目录下的前端与服务端全部源码，入口为 server/src/server.js，装配关系见 server/src/app.js。服务端按目录划分为 agent 7 个、routes 10 个、services 13 个、db 6 个、middleware 2 个、utils 2 个、config 1 个文件；前端覆盖页面、组件、hooks、store 与 services 共 43 个文件。数据库侧读取 server/migrations 下 6 个 SQL 脚本，重点确认表结构、索引与行级安全策略。依赖侧分别对根目录与 server 目录执行生产依赖漏洞审计。

运行配置在不泄露明文的前提下做了字段级核对，包括密钥长度与同值比对、跨域来源是否配置、数据库与向量库驱动、队列驱动、模型与精排开关。版本库侧确认了敏感文件的跟踪状态与工作区改动情况。本文不涉及业务数据的读取，所有结论均可用文中给出的文件与位置复核。

## 1.2　判定口径与证据类型

严重度按可利用性而非代码位置划分。严重指无需额外前提即可导致账号接管、全库数据泄露或核心数据损坏；高危指在常规部署下可稳定利用，或可在有限条件下造成同等后果；中危指需要特定配置、特定身份或并发时序才能触发；低危指加固项，单独利用价值有限，但会放大其他问题。同一根因在多个位置出现时按一处计入，避免重复计数。

证据分三类：一是代码行，文中给出文件与函数位置，可直接对照；二是命令实测，包括版本库跟踪清单、工作区状态、依赖审计结果与密钥同值比对；三是配置实测，即运行环境变量文件的实际取值。凡属推算的内容均标注为推算并给出假设，不与实测结论混写。

# 2　安全维度

安全维度共确认 14 项问题，其中严重 2 项、高危 4 项、中危 6 项、低危 2 项。问题的共同特征是信任边界画错了位置：要么把不该长期有效的凭据长期保留，要么把客户端声明当作事实，要么在服务端与数据库之间让渡了校验职责。

## 2.1　身份与会话：密钥治理是最薄弱的一环

最直接的入口是密钥。server/.env.example 中提交了 JWT\_SECRET 的一个 36 位取值，实测与 server/.env 中实际使用的值完全相同。这意味着版本库的读者可以离线签发任意用户标识的令牌；由于鉴权中间件在验签后按令牌中的用户标识回查数据库并直接采用该用户的角色，伪造一个管理员标识即可获得管理员权限，无需知道任何密码。示例文件本身还包含一个形似真实格式的模型 API Key，说明该项目长期存在把真实密钥写入示例文件的习惯，这也解释了为什么同值问题没有被发现。

在这条链路之外还有三处削弱：config/index.js 在非生产环境使用 hardcode 的默认密钥 enterprise-kb-secret-key-change-me，生产环境虽有 32 位以上的启动校验，但校验只发生在 NODE\_ENV 判定为生产时；令牌没有任何撤销机制，登出仅清空前端状态，改密接口更新密码后旧令牌仍然有效直到 7 天过期；refresh 接口对有效令牌直接重签，等价于无限续期。权限不足时中间件返回 401 而非 403，语义上把越权与未登录混为一谈，也会让前端把权限问题误判为登录失效。

## 2.2　访问控制：多处接口缺少主体与对象校验

第二类问题出在谁可以访问什么。文档列表、文档详情、搜索与推荐使用可选鉴权，未登录访问者可以读取全部已发布文档，对一个定位为企业内部的系统而言，这等于把知识库正文对外开放；若同时允许自助注册，外部人员注册后还能看到更多。用户信息接口 GET /api/users/:userId 与统计接口无需登录即返回邮箱、角色、部门与积分，积分排行接口同样免登录且返回用户对象，遍历自增标识即可批量导出全员通讯录，这是本文认为最容易被低估的一项。

对象级校验也有缺口。点赞与收藏接口不校验文档是否存在、是否对当前用户可见，草稿可以被任意登录用户点赞收藏，并触发按规则给作者加分，形成对未发布内容的刷分通道；评论创建接口既不校验文档可见性也不校验文档存在性，可以对草稿评论，也可以对不存在的标识写入孤立记录。索引任务查询与重试接口只要求登录，不校验文档归属，任何用户都能查看他人文档的索引状态，并通过重试接口反复触发重新向量化，把一个只读的运维接口变成了可计费的写入口。

## 2.3　输入与渲染：信任了两类不该信任的输入

前端渲染是本次最容易被忽略的高危面。文档详情页把正文交给 MDEditor.Markdown，该组件经由 @uiw/react-markdown-preview 引入 rehype-raw，默认解析并渲染原始 HTML，代码中没有 skipHtml、没有元素白名单、也没有对链接协议做约束。而正文来源是任意登录用户，注册又是开放的，令牌又存放在 localStorage，三个条件叠加后，一篇带事件属性的文档就能在浏览者（包括管理员）的会话中读取令牌并外发，构成从普通用户到管理员的横向提权。同一项目中的 Agent 对话框反而做了正确示范：skipHtml 加元素黑名单，并把链接降级为纯文本。

文件上传信任了客户端声明的类型。头像接口的文件名由原始文件名的扩展名决定，校验只看客户端提交的 MIME 是否匹配图片正则，而 MIME 由请求方自行填写。把内容为 HTML 的文件命名为 .html 并声明为 image/png 即可通过校验，文件写入后被 express.static 按扩展名以 text/html 返回，形成与 API 同源的存储型跨站脚本；若改用 SVG 扩展名，浏览器同样会执行其中的脚本。文档上传侧防护相对完整，有扩展名白名单、文件头嗅探与空字节检测，但 DOCX 交由 mammoth 在内存中解析，没有针对压缩炸弹的展开体积上限，10MB 的上传限制并不约束解压后的内存占用。

查询构造上有一处残余风险。db/supabase.js 的 cleanKeyword 会过滤百分号、下划线、括号、逗号与引号，随后仍以字符串拼接方式构造 PostgREST 的 or 过滤表达式，形如 title.ilike.%关键词%、content.ilike.%关键词% 与 tags.cs.\[关键词]。过滤字符挡住了大部分结构性注入，但反斜杠与通配语义未处理，关键词中的点号与星号仍可能改变表达式的解析结果。考虑到后端使用绕过行级安全的 service\_role 凭据，任何拼接式查询都应按参数化方式重写，而不是继续依赖字符黑名单。

## 2.4　数据与基础设施

环境变量文件没有被 .gitignore 覆盖，规则里只有 .runtime/ 与 \*.local，真实密钥目前只是因为从未提交才没有泄露。这属于靠习惯而非靠机制保护，一次误提交就会把模型密钥、Supabase service\_role 与对象存储密钥同时暴露。数据库侧的行级安全被明确关闭，迁移脚本注释写的是后端直接调用因此不启用策略；问题在于 Supabase 项目的匿名密钥默认对客户端可见，一旦该密钥以任何形式流出，全部表都可被匿名读取，包括用户邮箱与长期记忆中的历史问答。

对象存储上传设置了 X-Bz-Content-Sha1 为 do\_not\_verify，等于关闭内容完整性校验，上传内容在传输途中的篡改不会被发现；上传失败时把 B2 的原始响应体拼进错误消息，最终可能经错误监控接口或日志外泄。跨域策略在实际运行环境没有配置来源白名单，回退为通配，与示例文件中的 localhost 不一致；应用未引入任何安全响应头，没有 CSP、HSTS 与 nosniff，这会让前述存储型脚本问题更难被浏览器缓解。健康检查接口免鉴权返回能力开关，管理端指标接口把最近错误的原始消息前 500 字返回给管理员，两者都属信息暴露，危害有限。

安全维度的问题不是分布均匀的，而是集中在两个位置：一是凭据的生命周期，二是服务端对输入与对象的判断。前者需要一次彻底的密钥轮换与提交历史清理，后者需要把校验从客户端与数据库两层收回服务端。下表给出各维度的风险分布，完整清单见附录 A。

# 3　成本维度

成本维度共确认 9 项问题，其中高危 3 项、中危 4 项、低危 2 项。这里的成本既包括模型与向量化的直接计费，也包括数据库与网络传输、日志存储和重复计算的间接成本。共同特征是调用次数由配置上限而不是业务需要决定，且缺少按用户计量的预算约束。

## 3.1　检索路径：一次检索一次全表拉取

关键词检索的实现是本次成本问题的核心。knowledgeService.js 的 keywordSearch 以 status 为 published 调用 listDocuments，既没有传 page 与 pageSize，也没有限定返回列，Supabase 适配器在缺少分页参数时不会附加 range，查询最终以 select 全部字段的方式把所有已发布文档连同正文一次性返回。随后在 Node 进程内对每篇正文做小写化与子串匹配。这条路径的成本与文档总量线性相关：文档达到千篇量级时，每次检索都要传输全部正文，而单轮问答最多允许 3 次检索。

这条路径还有一个正确性副作用：当文档数超过 PostgREST 的返回行上限时，多出的文档不会被检索到，既不报错也不提示，表现为用户问某份明明存在的资料却答不知道。混合检索在此基础上还会对每个关键词候选再查一次库并重复计算一次关键词评分，形成 N+1 查询；精排则对最多 20 个候选、每个 500 字的片段做一轮交叉编码，单轮 3 次检索各触发一次。

## 3.2　模型调用叠加与重试放大

单轮问答的固定开销比表面看到的更高。每轮成功问答后，记忆服务会对问题与答案的拼接文本再做一次向量化，用于相似去重与写回；用户触发历史问答工具时再计一次；开启精排时再计一次精排请求。也就是说，一轮问答在模型调用之外固定叠加了两次向量化与一次精排，且这些调用没有结果缓存，同一问题重复提问会重复计费。

索引与抽取侧的成本同样由写入触发。每次文档保存，不论正文是否变化，都会重新入队向量索引并重新抽取知识图谱；抽取把正文截断到 12000 字后按 3000 字分片，最多 4 次模型调用，每个分片失败还会补抽一次。向量化按每批 10 条串行执行且不设重试，一次限流就会让整篇文档失败，然后由队列按 3 次上限重试，每次重试都从第一个分片重新开始，最坏情况下同一篇文档被计费三遍。

上限配置本身也构成风险。config/index.js 把单轮工具调用上限默认设为 300，可配置上限 400，而示例文件写的是 30，两者相差十倍；单轮模型调用上限 8、单次输出 2000 token、单轮超时 60 秒。工具层对检索另有 3 次的硬预算，读取体量由来源注册表限制在 24000 字符，这些护栏能挡住大部分失控场景，但它们靠的是运行期熔断而不是配置层的硬限额，一旦熔断逻辑被调整，成本曲线会立刻抬升。

## 3.3　护栏缺失

成本侧没有任何按用户或按租户的预算。系统没有 token 计量、没有日或月额度、没有超额告警，也没有成本看板；唯一的频率约束是会话存储中的每用户每分钟 10 次、每会话 200 次与单并发，而这些计数全部保存在进程内存，多实例部署后同一用户可以同时打到每个实例，限流被成倍放大。日志侧的成本也在累积：请求日志、每条审计的双份输出与检索链路上每次 5 到 7 条的诊断日志同时写标准输出，日志量随检索次数线性增长，而诊断日志中还包含上游错误响应体片段。

## 3.4　量化估算

把上述路径按配置上限折算，可以得到单轮问答与单篇文档的成本边界。需要强调这是上限推算，不是账单统计。字符到 token 的换算按中文约 1.5 字符每 token 估算，输入侧包含历史回放 24000 字符与来源预算 24000 字符。

表 2　成本路径的调用次数与体量上限

| 场景        | 触发次数上限        | 体量上限             | 放大原因              |
| --------- | ------------- | ---------------- | ----------------- |
| 单轮问答的模型调用 | 8 次           | 约 25 万输入 token   | 每次重发历史与来源，输入随轮次累积 |
| 单轮检索      | 3 次           | 每次全量已发布正文        | 检索不分页，select 全部字段 |
| 单轮精排      | 3 次           | 每次 20 候选、约 1 万字符 | 每次检索各触发一次，无缓存     |
| 单轮向量化     | 2 次           | 问题与答案全文          | 记忆检索与写回各一次        |
| 单篇文档入库    | 4 次抽取加 1 轮向量化 | 正文截断 12000 字     | 按 3000 字分片，失败补抽   |
| 单篇文档保存    | 同上，重复执行       | 同上               | 不论正文是否变化即重跑       |
| 失败重试      | 3 次           | 每次全量重跑           | 队列重试从首个分片重新开始     |

数据来源：本次审查依据 config/index.js 的默认上限、agent 与 services 目录下的调用路径推算；token 折算按中文约 1.5 字符每 token，属估算口径，不含实际账单数据。

按此推算，一次典型问答的输入规模在 1 万到 3 万 token 之间，而配置允许的最坏情形会接近 25 万输入 token，两者相差约一个数量级。真正决定账单的不是平均值，而是能否被外部触发到上限：登录不限流、注册不设门槛、工具上限三百、检索全表扫描，这四点叠加后，一次有组织的调用就能把单日预算消耗掉相当比例。

## 3.5　成本维度小结

成本问题的本质是把扩展性成本前置到了运行时。检索应当在数据库侧完成过滤与分页，抽取与向量化应当按内容版本幂等，精排与向量化应当缓存，配额应当按用户计量。这些改造并不需要重构架构，但需要在配置层设立硬上限，否则任何一次参数误调都会直接体现在账单上。

# 4　逻辑与一致性维度

逻辑维度共确认 10 项问题，其中严重 1 项、高危 2 项、中危 4 项、低危 3 项。与安全维度的外部攻击面不同，这一类问题在日常使用中就会发生，表现为数据被静默改坏、计数不准、并发丢失与状态不一致。

## 4.1　写入路径的数据完整性

最严重的一项在文档更新。db/index.js 的 updateDocument 先用展开运算符合并原文档，再显式覆盖 title、content、category 三个字段，取值直接来自入参；路由层把 req.body 原样透传，不做必填校验。只要调用方只提交部分字段，未提交的字段就会变成空值，随后写入的版本快照同样残缺，版本号还会照常加一。接口层测试或第三方调用很容易触发这一点，而前端因为提交完整对象掩盖了问题，属于典型的被主路径遮蔽的缺陷。

## 4.2　计数与积分的并发正确性

浏览量、点赞数、收藏数与用户积分都采用先读后写的实现。incrementDocumentViews 读取当前值加一后回写，高并发下后写者覆盖先写者，浏览量系统性偏低；点赞与收藏同样先查后写，重复点击与并发请求会得出不一致的计数；积分累加读取用户当前积分再加规则值，并发时丢失积分。这些字段本可以由数据库的自增或单条更新语句完成，实现的取舍把一致性责任放到了应用层。评论侧还有一处放大：创建评论会给作者加分，但没有任何每日上限，积分规则中定义的每日限额并未在累加路径生效，配合前述草稿可被互动的问题，刷分成本极低。

## 4.3　分页与上限缺失

分页参数的校验普遍只做了下界。文档列表、搜索结果、推荐列表、积分排行、用户文档列表与积分明细都采用取最大值不小于 1 的写法，没有上界；积分排行的 limit 直接进入查询，传入百万级数值即可让数据库一次性返回全表。这类问题单独看不构成数据泄露，但与免鉴权的用户接口组合后，就变成了批量导出全员信息的入口。

## 4.4　多实例与运行状态

会话存储是单进程实现，注释中也写明多实例需替换为共享存储。会话列表、限流计数、单并发标记与运行状态都保存在进程内 Map，多实例部署时同一用户可以在每个实例各跑一轮问答，单并发与每分钟十次的约束同时失效；会话容量检查虽读数据库，但缓存与运行态仍各实例独立。索引队列在 BullMQ 初始化失败时静默降级为内存队列，既不告警也不写审计，重启即丢任务，多实例之间也不共享，表现为文档上传成功但检索不到。

## 4.5　异常与审计链

进程级兜底对未捕获异常只记录不退出。Node 的运行模型下，未捕获异常发生后进程状态已不可信，继续服务可能带着损坏的内部状态处理后续请求，正确做法是记录后优雅退出并由进程管理器拉起。审计链也有断点：问答结束时的审计写入位于 finally 中，但排在会话落库之后，若落库抛错则本轮审计丢失；问答完成后的记忆写回入队没有捕获异常，失败会变成未处理的 Promise 拒绝。此外，注册接口不校验邮箱格式、不校验密码强度、不做邮箱验证，默认角色即为普通用户，等于把内部知识库的读权限开放给任何能访问服务的人。

## 4.6　逻辑维度小结

这一类问题的修复成本最低、收益最直接：更新接口补字段兜底与校验、计数改为单条原子更新、分页补上界、限流与并发控制外置到共享存储、异常改为记录后退出。它们不改变产品形态，但决定了系统能否被放心地交给多人使用。

# 5　稳定性与工程质量

稳定性与工程侧共确认 7 项问题，其中高危 1 项、中危 4 项、低危 2 项。这一维度的问题不会立刻表现为漏洞，但决定了前四类问题能否被及时发现和修复。

## 5.1　单进程假设贯穿全系统

除会话存储外，错误计数、最近错误环形缓冲、审计写入的串行 Promise 链、索引队列的内存实现都建立在单进程前提上；启动入口只在收到信号时关闭 HTTP 服务，没有停止队列、没有关闭 Redis 连接、没有等待在途任务，进程退出时可能存在未落库的会话与未完成的索引任务。对一个已经使用托管数据库与托管向量库的项目而言，应用层反而是最难水平扩展的一段。

## 5.2　观测与日志只在本地

审计以 JSON Lines 追加到本地 .runtime/logs 目录并按天切分，错误监控是进程内计数加最近 100 条缓冲，两者都在重启后丢失或清空；部署到多实例或容器后，日志分散在各实例本地磁盘，无法聚合检索。系统没有请求标识，一次问答跨多个服务调用无法串联；指标接口只对管理员开放，且返回的是错误原文而非结构化指标。

## 5.3　配置与文档漂移

示例配置与实现已经脱节：示例文件写 DB\_DRIVER 默认 local 并描述为内存数据库，而初始化逻辑只支持 Supabase，未配置即直接抛错；RAG 段注释仍写纯 JS 向量库持久化到 .runtime/vectors.json，而实际默认驱动是托管向量库；工具调用上限示例写 30、代码默认 300。这类漂移会让新环境按示例配置启动即失败，也会让运维误判系统行为。

## 5.4　测试与仓库卫生

仓库中只有一个测试文件 test/agentStream.test.mjs，服务端没有测试目录。以本项目当前的写入路径复杂度，文档更新、计数累加、检索降级、队列重试都没有回归保护，前述严重缺陷正是缺少接口级测试的直接结果。仓库根目录已跟踪两个与本项目无关的简历生成脚本，工作区还有一个个人简历 PDF；.github 目录为空，没有持续集成。检索与精排链路中遗留了大量以 rerank-diag 为前缀的诊断日志，生产环境每次检索输出 5 到 7 条包含请求地址、候选数量与上游错误体的记录。

## 5.5　稳定性与工程小结

这一维度的整改不产生直接的安全收益，但它决定修复速度。建议把 CI 与最小回归集放在与安全修复同一批次内完成，否则后续每次修复都缺少验证手段。

# 6　依赖漏洞

依赖审计以官方源执行，覆盖生产依赖。服务端共 4 项，其中严重 1 项、高危 2 项、中危 1 项；前端共 2 项，均为高危。四项均可通过升级修复，没有需要替换生态的项。

# 7　整改路线与优先级

整改顺序按攻击面收敛、成本控制、一致性修复、工程补强的优先级展开。理由是三处结构性缺口中的两处（密钥与渲染）只需要改配置与组件用法，投入最小而收益最大；访问控制的修复依赖接口逐个补齐，工作量中等；成本改造涉及检索实现与配置层硬限额，需要联调验证；一致性改造涉及数据库语句，风险相对可控但需回归测试。

# 8　结论与限制

结论明确：项目存在漏洞，且风险不是均匀分布在代码各处的小问题，而是三处结构性缺口的外显。第一处是凭据治理，示例文件与实际密钥同值，令牌不可撤销，等于把身份系统的根交给了版本库的读者。第二处是信任边界，原始 HTML 被渲染、客户端声明的文件类型被采信、查询以字符串拼接、草稿可被任意用户互动，服务端在多个位置把判断权让给了外部。第三处是单实例假设，会话、限流、队列、观测全部建立在单进程内存上，一旦扩容，限流与一致性同时失效，而这些失效在监控里看不出来。

按当前状态评价，项目在功能完整性上已经具备可用性，在安全性上不具备对外开放的条件。若部署在内网且仅对可信员工开放、关闭自助注册、不接入公网，三处严重问题中的渲染与密钥问题仍应修复，但整体风险可控；若要接入公网或允许外部注册，则必须完成 P0 与 P1 的全部事项后再上线。

本次评估的限制有四条。一是静态审查，未对运行中的服务发起爆破、注入或越权验证，因此文中严重与高危项的可利用性基于代码推理，未经实测确认；二是成本结论依据配置上限与调用路径推算，未取得真实账单与用量数据，实际金额可能显著低于上限；三是依赖结论仅覆盖当前已安装的依赖树，未做供应链来源与许可证审计；四是未读取生产日志做峰值与异常行为分析，因此对已发生的滥用无法给出判断。建议在联调环境对三项严重问题与四项访问控制高危做一次针对性复测，并以复测结果作为整改验收依据。
