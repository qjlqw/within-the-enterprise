# 当前 Agent 服务项目审查与市场可用性评估

审查日期：2026-11-06  
审查范围：`src/`、`server/src/`、数据库迁移、配置样例、测试与构建脚本  
审查方式：静态代码审查 + 现有测试/类型检查/生产构建

## 1. 项目是什么

这是一个企业内部知识库与知识助手系统，采用前后端分离架构：

- 前端：React 19、TypeScript、Vite、Ant Design、Zustand。
- 后端：Node.js 20+、Express、JWT、bcrypt、Zod、LangChain。
- 知识库：文档 CRUD、Markdown/TXT/DOCX 上传、版本、搜索、评论、点赞、收藏、积分。
- Agent：登录用户会话、SSE 流式回答、工具调用、来源引用、停止生成、反馈、会话持久化。
- RAG：Embedding、向量检索、可选 Rerank；可接 Upstash Vector。
- 异步任务：文档索引、知识抽取、问答记忆写回；可选 BullMQ/Redis。
- 持久化：当前代码主路径直接使用 Supabase service role；另有未完成的 hosted/adapter stub。

项目定位适合“企业内部知识库 + 受控问答助手”的一期产品，不是通用自主 Agent 平台。

## 2. 总体结论

| 维度 | 结论 | 说明 |
|---|---|---|
| 功能完整度 | 中等 | 核心文档、权限、Agent、RAG 链路已经具备，但部分能力仍是演示或降级实现。 |
| 安全状态 | 不达标 | 存在疑似真实 API Key、存储型 XSS 风险、缺少全局限流、默认弱配置和上传/内容边界问题。 |
| 逻辑正确性 | 中等偏低 | 已有幂等、并发限制、来源复核；但数据配置漂移、上传元数据丢失、计数竞态等问题会影响生产行为。 |
| 质量检测 | 部分通过 | 类型检查和前端构建通过；SSE 测试通过；部分服务端测试因远程 Supabase/网络依赖失败。 |
| 市场使用 | 当前不建议 | 完成 P0/P1 修复、真实环境压测、数据隔离验证和运维补齐后，可先面向小规模内部试点。 |
| 成本 | 中等，可控 | 最大成本来自 LLM、Embedding、知识抽取和 Rerank；当前默认配置会同时打开多项外部调用。 |

## 3. 已确认的高风险问题

### P0：疑似密钥已进入版本管理

文件 [`server/.env.example`](../server/.env.example:16-20) 的 `LLM_API_KEY` 不是占位符，而是一串形似真实模型密钥的值。该文件已被 Git 跟踪。

风险：任何能读取仓库、构建产物或代码评审记录的人都可能获得该凭据，造成模型账户盗用和费用损失。

处理要求：

1. 立即在模型服务商后台撤销/轮换该 Key，不能只修改文件。
2. 将样例值替换为 `LLM_API_KEY=` 或 `<set-in-secret-manager>`。
3. 检查 Git 历史、CI 日志和构建缓存；如真实密钥曾提交过，应按已泄露处理。
4. 生产环境改用 Secret Manager，禁止把密钥写入前端 `VITE_*` 变量。

### P1：文档详情页存在存储型 XSS 风险

[`src/pages/document/Detail.tsx`](../src/pages/document/Detail.tsx:224) 使用 `MDEditor.Markdown` 渲染用户可提交的 Markdown。该预览链路包含原始 HTML 处理能力；后端没有看到统一的 Markdown 白名单清洗策略。

风险：恶意用户发布带 HTML/事件属性的内容后，其他用户打开文档可能执行脚本，窃取 JWT、修改页面或发起已登录操作。

处理要求：

- 统一使用 `react-markdown` + `rehype-sanitize`，或在服务端存储前清洗并在前端再次限制。
- 禁止 `script`、`iframe`、事件属性、危险 URL 协议和任意 HTML 属性。
- 为文档内容增加 XSS 回归测试，至少覆盖 `<script>`、`onerror`、`javascript:`。

### P1：数据库配置与实际实现不一致

`server/.env.example` 声明 `DB_DRIVER=local`，但 [`server/src/db/index.js`](../server/src/db/index.js:58-64) 的 `initDb()` 始终连接 Supabase，且 [`server/src/db/adapter.js`](../server/src/db/adapter.js:21-23) 仍是未实现的 stub。

结果：本地开发、测试和部署说明会误导使用者；没有 Supabase 时服务启动或测试会失败。当前知识检索测试已出现 `TypeError: fetch failed`，与外部数据服务不可达一致。

处理要求：明确只支持 Supabase，删除误导性的 local 配置；或真正实现 local 测试适配器，并在 CI 使用它。不要保留“配置可切换但行为不可切换”的状态。

### P1：上传原文件的存储元数据没有持久化

[`server/src/routes/documents.js`](../server/src/routes/documents.js:244-265) 上传到 Backblaze 后只给内存中的 `doc.storage` 赋值，没有将该字段写回数据库。之后删除文档时 [`server/src/routes/documents.js`](../server/src/routes/documents.js:346-363) 依赖 `doc.storage` 找到对象，因此重启或重新读取文档后无法删除对应文件。

结果：对象存储产生孤儿文件，长期增加费用，并且删除语义不完整。

处理要求：给 documents 增加受约束的 `storage` JSONB 字段，上传成功后原子写入；删除采用 outbox/可靠任务，失败可重试并可观测。

## 4. 高风险与中风险问题

### P1/P2：接口缺少统一限流和严格分页上限

搜索、推荐、积分、文档列表、用户文档等路由把 `pageSize`/`limit` 直接传给数据库，只做了最小值，没有最大值。登录、注册、改密、评论和头像上传也没有 IP/账号级限流。

风险：大范围查询、请求洪泛、评论/注册滥用和模型费用失控。Agent 自身有每分钟 10 次限制，但不是全局 API 限流。

建议：统一 `zod` 查询 schema，分页上限 20/50；引入 Redis 或网关限流；对登录、注册、Agent、上传分别设置配额和审计告警。

### P1/P2：JWT 方案缺少撤销机制，且默认配置仍可启动

[`server/src/config/index.js`](../server/src/config/index.js:33-50) 只有 production 模式才拒绝弱 JWT 密钥；其他环境会使用固定的 `enterprise-kb-secret-key-change-me`。JWT 有效期默认 7 天，改密码后旧 Token 仍然有效。

建议：所有非测试环境都要求显式密钥；缩短 Access Token 有效期，引入 Refresh Token 轮换或 token version；改密、禁用用户、管理员变更时撤销旧会话。

### P1/P2：点赞、收藏和积分更新存在竞态

[`server/src/db/index.js`](../server/src/db/index.js:257-305) 采用“先查询是否存在，再插入关系，再读取计数并更新”的多步流程，没有事务或数据库原子递增。并发请求可能造成计数不一致，重复积分或关系插入异常。

建议：使用数据库唯一约束 + 事务；计数用 `UPDATE ... SET likes = likes + 1`；积分写入使用幂等业务键，避免重试重复发放。

### P2：输入边界不统一

- 注册没有邮箱格式、密码长度和最大长度校验。
- 评论内容只判断非空，没有长度上限，可能制造大记录和大响应。
- `toNumberId()` 使用 `parseInt`，`4abc` 会被解析为 `4`，路径参数应使用严格整数 schema。
- 删除/回滚/查询等路由没有统一的 UUID/数字 ID 校验。

建议：所有路由使用 Zod schema；文本字段设置最大长度；无效 ID 直接返回 400，而不是静默转换。

### P2：多实例部署仍有状态一致性风险

虽然会话正文已写入 `agent_sessions`，但运行锁、限流窗口、AbortController 和部分队列状态仍在进程内 Map。多个实例可能同时接受同一用户的 Agent 请求，内存限流也可被绕过。

建议：把运行锁、幂等键、速率限制和任务状态统一放入 Redis/数据库；使用分布式锁并设置租约；SSE 连接与任务执行解耦。

### P2：静态上传目录和头像校验仍不够稳健

头像使用声明的 MIME 和原始扩展名，保存到公开 `/uploads` 目录。没有看到图片内容嗅探、重编码或旧头像清理逻辑。

建议：使用文件签名检测和图片重编码；文件名使用随机 ID；对象存储使用私有桶和短时签名 URL；删除/替换头像时清理旧对象。

### P2：错误与运维控制不足

- `server/src/routes/agent.js` 在 SSE 失败路径直接 `console.log("error", error)`，日志可能包含供应商错误细节。
- 健康检查返回功能开关，但没有区分数据库、队列、向量库、模型供应商是否可用。
- 进程级 `uncaughtException` 只记录日志，不退出；进程可能处于不一致状态。
- 审计日志本地文件写入，未见轮转、集中采集、脱敏和告警策略。

## 5. 已发现的功能/逻辑缺陷

1. 文档版本历史的“查看”按钮目前只是提示信息，不能真正查看指定版本：[`src/pages/document/Detail.tsx`](../src/pages/document/Detail.tsx:244-267)。
2. 前端点赞/收藏状态只存在组件内，刷新页面后可能重复尝试；应由服务端返回当前用户状态。
3. 文档详情页使用 `MDEditor.Markdown`，Agent 页使用 `react-markdown`，两条 Markdown 渲染规则不一致，安全策略和显示效果会漂移。
4. `server/.env.example` 默认打开 Agent、Wiki 抽取、长期记忆和 RAG；新环境若直接复制样例，可能在未评估配额时产生持续外部调用。
5. 文档删除后索引清理依赖异步队列；若队列不可用，短时间内可能仍被检索到，需要删除标记或查询层的软删除过滤。

## 6. 质量检测结果

截至 2026-11-06：

- `npm run type-check`：通过。
- `npm run test:agent-stream`：2/2 通过。
- `npm --prefix server test`：部分通过；文档解析、队列、会话等测试通过，知识检索相关测试因远程数据服务/网络不可达失败（`TypeError: fetch failed`）。
- `npm run build`：在沙箱内因文件访问权限失败；在获得非沙箱构建权限后成功完成 Vite 生产构建。
- 构建产物仍有超大 Chunk：`antd-vendor` 约 1.1 MB，主业务 Chunk 约 1.57 MB，gzip 后仍较大。
- `npm audit`：当前环境无法访问 npm audit 服务，不能据此判定依赖无漏洞；应在 CI 或可联网环境重新执行并锁定审计结果。

质量结论：可以通过“开发质量门槛”，不能通过“生产上线质量门槛”。缺少可重复的无外网集成测试、覆盖率门槛、安全回归测试、负载测试和真实数据隔离验证。

## 7. 成本评估

没有流量、文档量、模型价格和调用日志，无法给出可信的月度金额。按代码结构，成本驱动项如下：

1. **LLM 问答**：每次 Agent 请求最多多轮模型调用，输出和历史上下文都会影响费用。
2. **Embedding**：新建、发布、修改和重建文档都会产生向量调用；文档越长、版本越多，成本越高。
3. **知识抽取**：样例默认打开 Wiki 抽取，发布/更新文档会额外调用模型。
4. **Rerank**：启用后会增加一次外部排序调用和延迟。
5. **基础设施**：Supabase、Upstash Vector、Redis/BullMQ、对象存储、日志和监控均可能产生固定或按量费用。

成本判断：小规模内部试点通常可控；如果默认启用 Agent + RAG + Wiki 抽取 + Rerank，并允许大文档、高频问答和无界分页，成本会快速上升。上线前必须记录每次请求的 token、Embedding 字数、Rerank 次数、队列重试次数和供应商费用，按部门/用户设置预算和配额。

## 8. 上线前整改顺序

### 阻断上线（P0/P1）

- 撤销并轮换疑似泄露的模型 Key，清理 Git 历史和样例文件。
- 修复 Markdown/HTML XSS，补充安全回归测试。
- 统一数据库驱动策略，提供可重复的本地测试库或明确 Supabase 前置条件。
- 持久化对象存储元数据，补偿删除和失败重试。
- 增加全局限流、严格分页上限、注册/登录/上传/评论/Agent 配额。
- 所有非测试环境强制使用随机 JWT Secret，并实现 Token 撤销或版本号机制。

### 试点前完成（P2）

- 将点赞/收藏/积分改为事务和原子更新。
- 统一 Zod 输入校验与 ID 校验。
- Redis 化分布式锁、幂等键和限流。
- 图片重编码、私有对象存储、签名 URL、旧文件回收。
- 增加数据库、队列、向量库、模型供应商的分项健康检查。
- 增加压测、故障演练、备份恢复和权限矩阵测试。

### 体验与性能优化

- 通过路由级动态导入继续拆分前端 Chunk，减少首屏加载。
- 版本历史实现真实查看/回滚预览。
- Agent 流式输出增加服务端断线恢复和任务查询接口。
- 对文档内容、Embedding、Rerank 和知识抽取设置预算、缓存和去重。
- 将审计日志接入集中日志系统，并建立模型费用与错误率告警。

## 9. 最终判断

该项目已经具备内部知识库 Agent 的核心产品骨架，适合继续做小范围、受控数据的内部试点。当前不能宣称已经通过安全质量检测，也不应直接对外开放或承载高敏感企业资料。完成 P0/P1 整改、依赖服务可重复测试、权限与数据隔离验证、成本计量和故障演练后，再评估市场化部署。
